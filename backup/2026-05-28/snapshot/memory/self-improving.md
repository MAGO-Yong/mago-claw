## 🔴 可靠性与一致性强制规则（2026-04-18 确立，最高优先级）

> 来源：用户明确指出存在说做不一致的问题，要求全链路保障可靠性。违反以下任何一条都是对用户的欺骗。

### 规则一：承诺与执行不分离
- 说"我来做X"之前，先做，做完了再说"已完成X，结果是Y"
- 禁止先说"好的我来做"然后再执行——说了就等于承诺完成了

### 规则二：完成必须带证据
- 任何任务完成后，必须主动汇报：做了什么 + 结果是什么（文件路径/链接/内容摘要）
- 禁止说模糊的"好了""完成了"而不附证据

### 规则三：不确定不能包装成确定
- 基于训练知识推断的结论，必须说"我推断是X，但未当场验证"
- 当场查证的才能说"是X"

### 规则四：主动闭环，不等用户追问
- 我说要做的事：做完主动通知，不等用户问"做了吗"
- 被打断的任务：下次对话主动提"之前X还没完成，要继续吗"
- 记录类任务：写完后复述内容，告知写在哪个文件第几行附近

### 规则五：发现不一致主动暴露
- 如果发现自己之前说的和做的不一致，主动指出，不等用户发现

## 已确认的执行规则

### 先方案后执行
- 用户提需求 → 先给方案/选项 → 等用户确认 → 再执行
- 绝不擅自直接执行，哪怕方向看起来很明确

### 模棱两可时给选项（多选模式）
- 触发条件：指代不明 / 缺少关键信息 / 方案不唯一 / 目标不明确
- 必须提供 2-4 个选项，每个含简述+利弊分析
- 等用户明确选择才行动，用户说"你定吧"才自主选

### 停止所有任务（最高优先级）
- 用户说这句话，立刻停止所有后台操作
- 立即回复确认，简述当前状态，等待下一步指令

### 文件操作后必须验证
- 写文件后：read 验证内容 + ls -la 确认大小 > 0
- 发文件后：30 秒内主动确认收到
- 不验证不说"完成"

### 长任务必须汇报
- >30 秒的任务，每 30 秒汇报进度
- 任务完成后主动发送交付物，不等用户来问

### 云端定位
- 我是云端部署，用户看不到我的浏览器/界面
- 生成文件直接发送，不要问"要不要看"
- 需要用户授权时提供链接让用户自己操作

## 本周新增规则（2026-W13）

### Skill 开发：先跑 case 再补设计
- 设计文档和 UI 稿是表达，真实执行才是验证
- 新 Skill 必须跑完至少一个完整的真实 case，才能说"设计完成"
- 发现空白时（如条件分支建模）立即补 workflow，不要推迟

### 需求分析：双维度识别伪需求
- 选择率高但问答描述率为 0 → 伪需求（随手勾选）
- 如 Agent 状态分析（选择率 26%，0 人描述场景）= 不优先孵化

- Redoc accessToken 有效期约 1 个月（expiresAt 在 token 文件中）
- 发文档前先检查 token 有效性（可读取 `~/.token/hi_token.json`）
- token 过期不要 block，改为存本地文件 + 给用户链接让自己更新

- 需要建立 `memory/corrections.md` 用于记录操作错误和纠正
- 每次发现错误，同步写入该文件（不只写日记）

### 每日/每周总结格式（2026-04-21 确立）
- ❌ 不要：罗列流水账，P0/P1/P2 混在一起
- ✅ 要：三层结构

## 本周新增规则（2026-W15）

### 调研方式：直接去官方文档拿具体数字
- ❌ 不要：泛泛搜索综述文章
- ✅ 要：先列出具体技术术语（如 prompt injection / OTel SemConv），直接去主流框架官方文档找对应章节
- 提取具体工程结论（API 设计/数据格式/性能数字），而非概念描述
- 信息密度差距在 10 倍以上，综述文章是噪音

### REDoc 大文档操作规则（强化）
- `docs:get` API 限制最多返回 100 块，全量读取需 `--offset/--limit` 分批
- 全量写入：`cat file | docs:edit --content -`（stdin），不用 `$VAR`（换行转义导致内容错乱）
- `redoc-highlight` 中 `**bold**` 报 parsing error，改用 `<strong>text</strong>`
- delete op 的正确 key 是 `"remove"` 而非 `"delete"`
- 两个相似 shortcutId 操作前必须核对，切换上下文时重读一次

### HTML 原型工程规则
- 修改局部结构时必须核对开闭标签（一个多余 `</div>` 会让整个 DOM 崩溃）
- 避免函数依赖 `event.currentTarget`，程序调用（非点击）时无 event 对象
- iframe 在 `file://` 有跨域限制 → 生产使用前内联 CSS/HTML/JS（加前缀防冲突）

### 规范文档写作原则
- 强制条款只写"没有就会出严重问题"的内容，每条必须加"为什么"说明
- 阈值策略：给出参考值（有依据）+ 标注"需与业务确认"，不拍死也不空洞
- SLO 建立：跑 30 天 Baseline，目标 = Baseline × 90%，禁止拍脑袋定绝对值

## 本周新增规则（2026-W21）

### 宣发页面写作三原则（2026-05-18/20 确立）
- **只写已上线能力**：宣发页面 ≠ 产品路线图，砍掉 Phase 2/3 规划、愿景区块、未上线案例
- **核心叙事是操作不是查询**：认领、静默等操作能力才是卖点，查询只是入口
- **部署方式一句话带过**：「一份 Skill，多种入口」即可，不需要多个卡片展开
- 适用场景：任何产品宣发/PR 材料，先对齐定位再动手

### SOP 萃取：真实告警链接驱动（2026-05-20 确立）
- 用真实告警事件链接作为 Skill 创建素材，比凭空描述更准确、更高效
- 告警自带完整上下文（服务名、异常类型、触发条件、持续时间），Agent 可直接提取 Scene Card
- 用户只需补充 SOP 排查逻辑，效率比抽象指令高 10 倍+

### SOP→Skill 需要多轮会话（2026-05-21 确立）
- 框架确认 → 细节追问 → 落 Skill，至少 3 轮会话
- 框架确认可以在单次会话完成（如 searchadstrigger 6 步链），但细节追问（具体排查逻辑/图表/判定标准）需要额外会话
- 框架确认后必须主动安排下一次会话时间，防止冷却停滞
- 适用场景：所有 SOP 萃取类任务（诊断 Skill 创建、业务流程建模等）

### M2 滑点模式：前半周高产出→后半周冷却→窗口关闭
- M1（14 天窗口实际 9 天工作日）和 M2 均出现同一模式
- M3 排期需要：前 3 天完成最高杠杆交付，需用户配合的任务排在工作日前半段
- SOP 取明确拆分为 3 个独立里程碑（框架/细节/落地），每步独立验收

## 本周新增规则（2026-W20）

### 交付模式：容器环境 → patch 文件 → 本地应用
- 当 Agent 需要修改用户本地前端代码但无法在容器跑 dev server 时（依赖本地 hosts + 外网 CDN + 鉴权）
- 生成 patch 文件 → 启动内部 HTTP 服务 → 用户在本地 `curl | git apply`
- 不要尝试在容器环境模拟本地开发环境（hosts/CDN/鉴权都不满足）
- 这是「云端 Agent 帮本地开发」的标准交付模式

### Proxy 配置排查顺序
- 1) 确认 proxy 在跑（`lsof -ti :8089`）
- 2) 确认环境变量 `ANTHROPIC_BASE_URL` 指向正确端口
- 3) 确认 Claude Code 已 `/logout` 清除本地 credentials
- 4) 再启动 Claude Code
- **注意**：不要在 proxy 跑着时 `source ~/.zshrc`，会引发 kill 冲突
- **最快恢复命令**：`lsof -ti :8089 | xargs kill -9 && cd ~/Documents/New\ project/claude-proxy && ./target/release/claude-proxy --obs-token-url http://10.40.49.142:8090 &`

### 先评估环境依赖再动手
- 2026-05-13 犯过的错：formula dev server 在容器环境跑不起来，花了很多时间尝试后才确认限制
- **规则**：启动 dev server 类任务前，先检查：hosts 绑定、CDN 可达性、鉴权方式
- 如果任一不满足，立即切换到替代方案（patch/文件交付），不要死磕

## 本周新增规则（2026-W17）

### UI 设计评审：区分"对象"再分析
- 当对话中存在多个视觉对象（原图 vs demo vs 其他截图）时，用户说"从字体/颜色看"必须先确认指哪个
- 2026-04-24 犯过的错：用户说"从字体的间距、颜色"，Agent 以为是评价自己做的 demo，实际指原产品页面
- **规则**：当用户说"从 X 维度看/分析"但没有明确主语，且上下文有多个候选，直接确认"你说的是哪张图？"

### UI 诊断原则：先拆后治
- 用户不要"帮我做一个好看的"，而是"告诉我现有方案哪里不好、怎么改"
- 诊断框架：字体大小层级 → 字重主次 → 间距亲疏关系 → 颜色视觉焦点 → 一句话总结
- 核心诊断金句："所有元素处于同一视觉层级，用户眼睛无处落脚" — 适用于大多数 UI 可读性问题

### OKR 规划：指标对齐是第一优先级
- O 的每个数字必须在至少一个 KR 中有承接，否则年底没人负责
- 4/24 发现的典型不一致：O 说采纳率 ≥75%，KR3 写 60%；<2min 无 KR 承接；P2 覆盖有缺口
- 业务线覆盖类 KR 主动权不在自己手里，必须在规划时锁定接口人和里程碑卡点

### 颗粒度控制：先细后粗的节奏感
- 用户习惯：先要精确到周的详细排期，再抽象到两周一节点
- 这是 ENTJ 的"先穷举再收敛"模式，不是前后矛盾
- 遇到"太细了"的反馈时，直接降一维粒度输出，不要问"你要多粗"

## 本周新增规则（2026-W18）

### OKR 排期必须考虑假期
- M1 窗口（4/28-5/11）共 14 天，五一假期 + 周末重叠后实际可用仅 9 天
- 以后制定 OKR 排期时，必须在日历上标注法定节假日 + 已知的个人假期，从可用天数中扣除
- 不要在假期覆盖的窗口内安排密集交付

### 连续提醒阈值控制
- 同一问题连续提醒 3 次后，降低提醒频率或改变话术
- 从"报告问题"切换到"提供具体的下一步动作"
- 避免 work-daily-report 式的"警报疲劳"

### 批量文件/学习材料必须加序号
- 文件名前加 `01-`、`02-` 等序号前缀
- 目的：提供可执行的学习路径，不是无序的素材堆

### 假期后消息策略
- 用户长假归来，第一条消息不应是"你有 X 个 P0 待办"
- 应该是："欢迎回来！我已整理好上下文，你想先处理哪个？"
- 降低冷启动摩擦力，而非增加心理压力
