## 二、错误与纠正

### [纠正] 批量文件未加序号（4/29）
- **错误**：发送 LangChain Deep Agents 学习资料时，文件名是 `overview.html`、`quickstart.html` 等英文原名，无学习顺序标识
- **用户反馈**：「你的文件名给我写个序号呀」
- **纠正**：全部重命名为 `01-概览-Overview.html` 到 `12-ACP协议-ACP.html`
- **规则沉淀**：生成批量文件/学习资料时必须加序号前缀（已在 self-improving.md W17 有类似规则，本次强化）

### [纠正] GitHub PAT 过期未主动监控（5/1）
- **问题**：daily-backup cron 首次 push 失败（401 Unauthorized），GitHub Personal Access Token 过期
- **根因**：token 管理缺乏主动监控机制，只在失败时才暴露
- **影响**：工作区备份和版本管理暂时退化为本地状态
- **建议**：在 token 过期前 7 天主动提醒用户更新

### [纠正] 批量操作"说做分离"（4/27）
- **问题**：批量发送 12 篇 PDF 时，#7/#9/#11 三篇在对话文本中写了内容，但没实际调用 message 工具发送
- **根因**：thinking 中以为自己在发送，实际只是在 text 里输出了内容
- **教训**：写了 ≠ 发了。批量操作 + 交替使用工具时，容易漏掉工具调用
- **修复**：用户指出后补发

## 四、核心洞察

### 洞察 1：M1 窗口开启 = 假期开始 = 零执行

- 这是本次 OKR 规划时**未预料到的时间账**：M1 窗口 4/28-5/11 共 14 天，但五一假期（5/1-5/5）+ 周末重叠，实际工作日仅剩 9 天
- 假期前有效交互仅 4/27-4/29 三天，且主要精力不在 OKR 核心路径上
- **教训**：OKR 排期必须考虑法定节假日 + 个人假期。如果 OKR 窗口覆盖假期，应在规划时就扣除假期天数
- **数据**：14 天窗口 - 5 天假期 - 2 天周末 = 9 天可用工作日。OKR 4KR 在 9 天内完成，节奏极紧

### 洞察 2：协作学习模式的首次验证窗口

- 4/29 用户说「我会把不懂的丢给你记录」，建立了「用户主导 + Agent 被动记录」的新协作模式
- 这是用户首次主动将自己定位为"学习者"，而非"决策者"或"执行者"
- 假期中断了这个验证窗口，假期后需要观察：用户学习密度 vs 卡点密度 → 判断这个模式是否可持续
- **价值**：如果跑通，意味着 Agent 可以承担更被动的角色，不需要每次主动推进

### 洞察 3：连续零交互的"警报疲劳"效应

- work-daily-report 连续 5 次（4/28-5/2）输出相同结论（P0 拖延/零交互/方向二停滞）
- 这引发了一个新的 Agent 设计问题：**重复提醒是否从"有帮助"变成"噪音"？**
- 如果用户已经看过但选择不行动，继续报告同样的内容就是噪音
- **应对策略**：
  - 方式切换：从"报告问题"到"提供具体下一步动作"
  - 阈值控制：同一问题连续提醒 3 次后，降低频率或改变话术
  - 假期/旅行期间：降低 cron 提醒频率，假期后重新建立上下文

### 洞察 4：P0 待办拖延已进入"冷启动"阶段

- 3 个 P0 待办从 W16 延续至今，拖延天数从 9 天 → 11 天 → 15 天 → 假期后预计 19+ 天
- 拖延的本质不是用户不关心，而是**优先级排序**：LangChain 学习 + 旅行规划的优先级 > 技术债
- 但 M1 窗口已经启动，这意味着假期后需要**重新建立上下文**，而不是简单接着做
- 冷启动成本：用户需要重新理解 3 个待办的当前状态、阻塞点、下一步动作

### 洞察 5：用户决策节奏的再确认

- obs-token 流水线需求（4/29）抛出后，至今 5 天未确认 Agent 给出的 3 个方案
- 这延续了用户一贯的决策模式：先抛需求 → 等方案 → 不急着推进
- 不是"不想做"，而是"不急着做"。这是 ENTJ 用户的"战略耐心"——先让 Agent 调研清楚，再在合适的时机做决策
