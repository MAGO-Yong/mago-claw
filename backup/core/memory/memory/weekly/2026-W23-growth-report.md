## 🧬 核心洞察

### 1. 冷却模式从「认知」到「确诊」

W21 首次确认 M1→M2 同一模式（前半周高产出→后半周冷却），W22 确认第三次复现，W23 第五次确认。这不是偶然，是系统性行为模式。

**根因假设**（未验证）：
- SOP→Skill 需要 3 轮会话（框架→细节→落地），但框架确认后没有锁定下次会话时间
- 用户是 ENTJ，习惯「先穷举再收敛」，一旦进入冷却就难以自行重启
- 冷却期越长，重启摩擦力越大（18 天零交互 vs 3 天零交互，冷启动成本差 6 倍）

**这不是 Agent 提醒不够好的问题**——连续 7 天完整待办推送已证明「清单式提醒」完全失效。

### 2. P0 通胀 = 沉没成本陷阱

当一个 P0 被顺延超过 7 天，它已经从「优先级高」变成「提醒无效」。顺延 13-14 天的 P0 在心理权重上等同于「已放弃但未正式关闭」。

**新认知**：
- 顺延 >7 天的 P0 应从「待办」降级为「待确认是否关闭」
- 继续推送只会加剧警报疲劳，让用户对整个待办系统失去信任
- 正确做法：要么 5 分钟最小推进（能推进就推进，不能就正式关闭），要么接受现实清零

### 3. 自动任务运转良好但价值递减

cron 系统（daily-digest / work-daily-report / daily-backup / weekly-growth-report）连续 7 天 100% 正常运行，Git push 稳定。但这些任务在零交互周产生的全部是「状态确认 + 顺延天数 +1」，信息增量为零。

**反思**：自动报告在零交互周的价值是什么？不是提醒用户（已无效），而是为未来的复盘提供数据基线。

### 4. M3→M4 切换需要「清零」而非「继承」

M3 的 14 天遗留不是 M4 的起点。如果把 4 个 P0 + 7 个 P1 全部继承到 M4，M4 Day 1 用户看到的是一个 11 项的失败清单，这会进一步降低启动意愿。

**建议**：M4（6/9-6/22）首日只保留 1 个 P0（alipayservice 绑定），其余全部标记为「待确认」。完成一个再激活下一个。
