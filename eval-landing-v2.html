认知建立
评估是什么，以及三个常见误解

评估的定义是：用可量化的方式，持续回答「Agent 在真实场景里的综合表现是否符合预期」。评估关注的不是底层模型的通用能力，而是 Agent 在真实业务输入、工具定义、知识库内容和上下文条件下的实际表现——这是模型、工具、知识库三个维度的综合结果。

误解 01

评估是测模型能力

实际上

评估的对象是 Agent 在特定业务场景下的综合表现，而不是底层模型的通用能力。同一个模型，换一批工具定义或知识库内容，评估结论可能完全不同。模型能力的基准测试无法替代业务场景的评估。

误解 02

评估就是人工打分

实际上

人工是评估流程的最终确认环节，而不是主要手段。正确路径是：自动化机制从大量请求中把问题样本筛选出来，人工只处理被筛出的部分。没有自动化前置，人工评估的成本难以持续，覆盖面也极为有限。

误解 03

有通用评估器可以直接用

实际上

不存在对任意 Agent 都准确的通用评估器。不同业务对「好」的定义不同：客服 Agent 关注问题解决率，RAG Agent 关注检索相关性，Tool Agent 关注工具调用的参数准确性。业务 owner 需要自行梳理评估维度并孵化出适合自身场景的评估器——平台提供框架和执行机制，评估标准由业务侧定义。

问题定义
不做系统性评估，你在用什么替代它

这些做法在早期可以运转，但随着 Agent 复杂度和流量规模增长，代价会快速放大。

当前做法 实际代价
人工抽查几条对话，觉得还行就上线 Agent 一次请求可能经历多个节点（LLM 调用 / 工具调用 / RAG 检索），人工无法系统性覆盖完整链路。边界场景的问题持续漏过，直到用户投诉才被发现。
凭经验判断「新版好像比旧版好」 工具调用准确率可能在某次迭代中下降，RAG 检索质量可能在某次知识库更新后劣化。没有可量化的对比基准，迭代方向的正确性无法被验证，优化效果无法被复现。
发现 bad case 后存入飞书文档 下次迭代后，这个问题是否被修复？同类问题是否再次出现？没有自动化的回归机制，只能依赖人工记忆追踪，覆盖面和可靠性均无法保证。
从未系统性查看过 Agent 的完整对话链路 这是最容易被忽略的盲区：Agent 在真实运行时经历了什么——用户的完整输入、每次工具调用的参数和返回、每次 LLM 调用的实际 Prompt 和输出、最终给用户的回复——没有一个地方可以系统性地看到这些内容。
评估地图
评估贯穿 Agent 开发的全周期

评估不是「上线时做一次」的动作，而是贯穿 Agent 从开发到持续运营全周期的机制。不同阶段面临的问题不同，对应的评估路径也不同。

01

开发阶段

有 bad case，验证修复是否有效
典型处境 Agent 还未上线或刚完成一次迭代。手上有已知问题样本，修改了 Prompt、工具实现或知识库后，需要验证改动是否真正解决了问题，以及有没有引入新的劣化。
评估路径
整理 bad case 数据集 → 配置评估器 → 离线回放 → 对比版本得分
关键价值：bad case 从「存在文档里」变成「可重复自动验证的回归集」，每次迭代后跑一遍，修复验证才真正形成闭环。
02

上线前

建立质量基线，再灰度放量
典型处境 Agent 准备上线或扩大灰度范围。需要在真实流量进入之前，确认整体效果处于可接受范围，并明确知道哪些场景存在风险——不是凭感觉，而是有数据支撑。
评估路径
整理代表性样本集 → 定义评估维度 → 离线评估 → 查看得分分布
关键价值：上线前明确知道哪些场景还有问题、哪些风险是可接受的，比在真实流量中被动发现问题的排查成本低得多。
03

上线后

持续监控，自动发现 bad case
典型处境 Agent 已在运行，每天有真实用户请求。某个工具最近开始频繁调用失败、某类 query 的 RAG 召回质量在下滑、某次模型升级后某个场景悄悄劣化——这些问题不会主动暴露，需要持续监控机制来发现。
评估路径
X-RAY 采集完整链路 → 自动周期评估 → 实验报告 → 低分样本自动入库
关键价值一：配置一次，持续自动运行，问题样本自动沉淀。
关键价值二：X-RAY 采集的链路数据本身就是价值——这里是系统性查看 Agent 完整对话链路的唯一入口。
04

版本迭代

验证每次改动有没有引入劣化
典型处境 Agent 在持续迭代：Prompt 在调整、工具在更新、模型版本在升级、知识库在扩充。每次改动都可能在解决一个问题的同时引入新的问题，需要在发布前进行回归验证。
评估路径
复用已有数据集 → 迭代后重新跑评估 → 对比版本得分变化
关键价值：数据集随线上 bad case 的持续回流而不断积累，回归验证的覆盖面越来越广，数据集越跑越有价值。

评估粒度
三种评估粒度，对应不同的诊断深度

根据需要定位问题的精度选择评估粒度。粒度越细，能发现的问题越具体，配置成本也相应增加。通常从结果评估开始建立基线，再按需引入节点评估或轨迹评估。

入 → 出
结果评估
只看最终输入和输出
适用场景
建立质量基线、上线前验收、持续监控整体效果水位
✓ 能发现：回答幻觉、答非所问、格式错误、安全违规
✗ 发现不了：具体是哪个节点出了问题
典型案例

用户问「帮我查最近三个月消费记录」，Agent 经历了多次工具调用和 LLM 推理后返回结果。结果评估只判断最终回复是否准确完整——适合快速建立整体质量感知，不需要深入链路细节。

入 → ● → 出
节点评估（单 SPAN）
拆开每个执行节点单独评估
适用场景
已知问题出在某个具体环节，需要精确定位和持续监控该节点的质量
✓ 能发现：某次 LLM 调用输出质量下降、工具参数传错、RAG 检索未召回正确内容
✗ 发现不了：步骤之间的逻辑因果关系是否合理
典型案例

Agent 在调用搜索工具时，生成的查询参数质量参差不齐。单独对「工具调用 SPAN」做评估，判断每次生成的 query 是否准确覆盖了用户意图——只聚焦这一个节点，不需要看整条链路。

T → A → O → T → A → O
轨迹评估
评估 Agent 内部执行逻辑的合理性——步骤之间的因果关系是否成立
适用场景
链路较长、结果时好时坏、但无法定位具体问题环节的深度诊断
✓ 能发现：逻辑断裂点（Observation 未被下一步 Thought 有效利用）、意图在传递中被稀释、冗余执行步骤
✗ 注意：这是诊断工具，适合定位问题根因，不建议作为常规全量监控手段
评估方式：将 ReAct 轨迹拆解为「因果对」逐对判断
Thought 推理结论是否被后续 Action 忠实执行？
↓
Action 工具调用结果是否被正确解析为有效信号？
↓
Observation 本步结果是否被下一步 Thought 有效利用？

任意一个因果对判断为 No，即为逻辑断裂点，定位到该步骤后可针对性优化。

配置机制
评估器与数据来源

评估器是评分的执行单元，数据来源决定评估的覆盖范围。两者的配置是评估体系落地的核心工作。

评估器类型
LLM 评估器 推荐起点

通过 Prompt 描述评分标准，由大模型对每条样本给出 score 和 reason。适合需要语义理解的维度：相关性、正确性、幻觉、意图匹配等。

优势上手快，无需开发，灵活应对语义复杂度高的判断
注意每条样本消耗 token，不适合全量运行；评分准确性依赖所选模型的能力
HTTP 评估器

将业务已有的判分逻辑封装为 HTTP 服务，平台调用该服务获取评分。适合规则明确、已有 checker 服务，或需要进行全链路评估的场景。

优势稳定可控，可复用已有业务能力，支持全链路评估模式
注意需自行开发并维护评估服务，返回格式须符合平台规范
人工评估不是独立流程，而是接在自动化评估之后的最终确认环节——自动化先筛出低分样本，人工只处理被筛出的部分。
数据来源
⚡
在线链路数据

X-RAY 从真实请求中采集完整链路，包含用户输入、每个 SPAN 的输入输出（LLM 调用 / 工具调用 / RAG 检索）、最终响应。通过 JsonPath 将指定字段注入评估器。

适合：线上持续监控、自动发现 bad case
📋
离线数据集

手动整理的样本集，或从线上低分样本自动回流的数据。设计好输入/期望输出/标签等字段，字段映射至评估器变量后执行评估。

适合：开发阶段验证、上线前基线建立、版本迭代回归

⚠️ 最常见的配置问题

评估任务完成后，发现 reason 全部不准确，认为「评估不准」。

实际原因：90% 的情况是字段映射配错了，评估器接收到的不是需要被评估的内容。

排查方法：进入实验报告 → 任意一条样本 → 查看详情 → 找「评估器入参」一栏，确认传入的字段值是否符合预期。字段映射正确，评估器才能给出有意义的判断。
