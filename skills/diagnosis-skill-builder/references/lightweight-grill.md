# 轻量 Grill 方法

这份文档把 `$grill-with-docs` 的方法论裁剪到告警 Skill Builder 里。它用于创建阶段把模糊的排障经验问清楚，不是新的诊断 SOP。

## 目标

在生成告警 Skill 前，把三类问题问清楚：

- 场景边界：这个 Skill 覆盖什么告警，不覆盖什么告警。
- 术语边界：用户说的“服务、指标、根因、异常、恢复、误报”等词具体指什么。
- 证据边界：哪些判断可以用 `xray-cli` 或已登记 `diagnosis-cli` 能力自动取证，哪些只能作为依赖缺口或人工背景。

## 追问方式

一次只问一个关键问题。每个问题都带推荐答案，让用户只需要确认或修正。

格式：

```text
我建议这样定：{推荐答案}。
这个理解对吗？如果不对，应该改成什么？
```

不要一次抛出长表单。不要为了完整性追问所有边角。优先问会影响运行时行为的问题。

## 能查就不要问

如果问题可以通过已有信息回答，先自己查：

- 用户给了告警 ID：用 `xray-cli` 查告警上下文。
- 用户给了 rule id：用 `xray-cli` 查规则和触发条件。
- 用户给了 service/app：用 `xray-cli`、已登记 `diagnosis-cli` 能力或已有 artifact 确认稳定名字。
- 用户要求查变更事件：优先用 `diagnosis-cli change query <app>`，但时间窗、app 和失败策略必须明确。
- 用户给了已有 Skill/SOP：直接读 artifact，抽取术语、流程和缺口。
- 需要核对运行环境：读取 `alarm-skill-agent-boundary.md`。

只有查不到、查出来有冲突、或会影响生成 Skill 行为时，才问用户。

## 术语校准

用户使用模糊或冲突词时，立即收敛成生成 Skill 中的标准说法。

示例：

- 用户说“服务挂了”，追问是指 service 不可用、接口成功率下降、QPS 为 0，还是告警平台无数据。
- 用户说“误报”，追问是采集延迟、规则阈值问题、业务低峰，还是告警恢复太快。
- 用户说“根因”，追问是需要确定根因，还是只输出最可能方向和下一步证据。

术语一旦确认，写进生成的 Skill 的说明、输入契约、报告字段或术语表。不要只停留在聊天里。

## 场景压测

用具体场景压边界，而不是抽象讨论。

优先压这些边界：

- 告警缺少 service/app 时怎么办。
- `xray-cli` / `diagnosis-cli` 查不到数据时是 unknown、blocked，还是跳过该节点。
- 同一规则在多个服务上触发时，Skill 是走同一流程还是按 payload 路由。
- 指标正常但日志异常时，报告该怎么表达。
- 证据不足时，是否允许输出“疑似根因”。

每个压测只问一个问题，并给推荐答案。

## 代码和文档核对

当用户说“运行时能做某事”或“某个能力可用”时，优先核对现有代码、文档或边界文档。

如果发现冲突，直接指出：

```text
你说这里可以依赖 {能力}，但目标 Agent 边界里没有这个运行时依赖。我建议把它标成依赖缺口，除非你能把证据改成 xray-cli 或已登记 diagnosis-cli 能力可取。这样定吗？
```

不要把冲突静默吞掉，也不要为了让流程完整而编造能力。

## 即时沉淀

确认一个决定，就把它写进生成的 Skill 草稿：

- 术语决定写进术语表或报告字段。
- 输入决定写进输入契约。
- 证据决定写进自动节点或依赖缺口。
- 失败策略写进节点说明。
- 不覆盖范围写进适用场景或边界。

不需要为这个 Builder 创建 `CONTEXT.md` 或 ADR。这里的“文档沉淀”指沉淀到生成的告警 Skill 包里。

## 停止追问

满足以下条件就停止 Grill，进入生成或验证：

- 场景边界清楚。
- 运行时输入清楚。
- 每个自动节点都能对应到 `xray-cli`、已登记 `diagnosis-cli` 能力或明确为缺口。
- 失败策略清楚。
- 用户已经接受当前诊断流程。

如果继续追问只会扩大范围，就停止。
