# 告警 Skill 验证循环

这份文档用于指导告警诊断 Skill 的真实验证和迭代。它不是新的排障 SOP，而是 **开发 -> 验证 -> 开发** 的质量收敛方法。

## 目标

用真实历史告警验证 Skill 是否能稳定执行，让每一轮验证结果驱动下一轮开发，并在少量循环内收敛。

建议目标：**5 次循环内收敛**。

验证前先确认 `xray-cli` 版本不低于 `v0.0.31`。如果版本不满足，先按 `xray-cli-setup.md` 安装或升级，再开始 upload/test 循环。

如果本轮 Skill 使用 `diagnosis-cli`，还要先确认 `diagnosis-cli --version` 和对应子命令 `--help` 可执行。当前只允许验证 `diagnosis-cli change query <app>` 变更事件查询能力；缺失或不可用时不要继续伪造取证结果，应把该节点改成 `blocked` / `dependency_gap`。

如果 5 次后仍无法稳定，不要继续盲目补逻辑。应暂停迭代，重新检查：

- 场景是否太大，需要拆成更小的告警 Skill。
- 输入是否不稳定，例如缺少 `alarm-event-id`、service、app、时间窗或 rule 信息。
- 证据是否超出 `xray-cli` 或已登记 `diagnosis-cli` 能力边界。
- 判断规则是否模糊，导致 Skill 无法给出稳定结论。
- 失败策略是否缺失，导致空数据、权限失败、字段缺失被误判。

## 循环步骤

每轮按固定顺序执行：

1. **开发一个最小改动**

   本轮只处理一个主要问题，例如输入解析、一个 `xray-cli` / `diagnosis-cli` 取证节点、一个判断规则、一个失败策略或一个报告表达问题。不要一次性塞入多个未经验证的分支。

2. **上传版本**

   ```bash
   xray-cli alarm skill upload <skill_dir>
   ```

3. **用历史告警测试**

   ```bash
   xray-cli alarm skill test --skill-name <skill_name> --alarm-event-id <历史告警记录>
   ```

4. **观察输出过程**

   不只看最终结论，重点看：

   - 是否触发了预期 Skill。
   - 是否读取了正确的告警上下文。
   - 是否只调用已登记的只读原子能力。
   - 是否没有运行时用户交互。
   - 是否没有不必要写操作。
   - Python 脚本是否只依赖标准库。
   - 失败、空数据、字段缺失是否被清楚报告。
   - 结论是否有真实证据支撑。

5. **回到开发**

   每轮只改最关键的问题，避免一次塞入多个互相影响的变化。

   优先修：

   - 输入解析错误。
   - `xray-cli` / `diagnosis-cli` 命令参数错误。
   - 证据字段读取错误。
   - 失败策略缺失。
   - 报告结论和证据不匹配。

6. **重复循环**

   再次开发、upload、test、观察。记录每轮改动和结果。

## 使用 subagent 拆分验证

如果当前开发环境支持 subagent，建议把验证循环拆成三个角色执行。这样主 Agent 不会同时承担执行、观察和修改判断，能更快发现偏差。

推荐拆分：

- **执行 subagent**：只负责运行 `xray-cli alarm skill upload` 和 `xray-cli alarm skill test`，收集命令、返回码、stdout/stderr、耗时和关键日志。
- **观察 subagent**：只负责读测试输出，判断是否违反三条原则，是否有无证据结论、错误取证、交互依赖、写操作、Python 第三方包依赖或失败吞掉。
- **修改建议 subagent**：只基于观察结果提出最小修改点，避免扩大 Skill 范围。

主 Agent 负责决策：

- 是否接受修改建议。
- 是否进入下一轮开发和 upload/test。
- 是否已经收敛。
- 是否超过 5 次循环后需要缩小场景或拆分 Skill。

subagent 只用于创建和验证阶段。生成后的告警 Skill 运行时仍必须自洽，不能依赖 subagent、其他 Skill 或人工协作。

## 5 次内收敛建议

推荐节奏：

- 第 1 次：确认 Skill 能触发，输入能解析。
- 第 2 次：确认核心 `xray-cli` / `diagnosis-cli` 取证能跑通。
- 第 3 次：确认判断规则和异常/正常/未知状态能区分。
- 第 4 次：修报告表达和失败策略。
- 第 5 次：只做收尾，不再扩展新能力。

如果第 5 次还需要新增大分支、新数据源或新规则，说明当前 Skill 边界还没切清楚。应先缩小场景或拆分 Skill。

## 收敛标准

可以认为本轮 Skill 已收敛，当它在目标历史告警上满足：

- 能稳定触发并完成运行。
- 自动取证只使用 `xray-cli` 原子能力、已登记的 `diagnosis-cli` 原子能力或 Skill 内部封装。
- 运行时不向用户提问。
- 不依赖其他 Skill 或第三方 Python 包。
- 不做生产写操作；临时写入只在 `/tmp`。
- 关键结论有证据；证据不足时明确输出未知或依赖缺口。
- 报告能让告警处理人知道下一步该看什么。

## 不要做的事

- 不要为了通过一次测试而硬编码某个历史告警的结论。
- 不要在第 4、5 轮继续扩大 Skill 覆盖范围。
- 不要把非 `xray-cli` / `diagnosis-cli` 证据伪装成自动取证。
- 不要把失败吞掉后输出确定性根因。
- 不要依赖运行时安装包、交互登录、浏览器状态或持久文件。
